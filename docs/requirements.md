# portfolio-chanoka-app 実装範囲

**このファイルはリポジトリごと公開する前提で書く。** 実在の氏名・屋号・実ドメイン・単価は書かない。

最終更新: 2026-08-13（実装範囲の確定）

## 位置づけ

副業ポートフォリオ第3弾。第1弾 `portfolio-demo-store`（Shopifyテーマ実装）、
第2弾 `portfolio-booking-app`（Laravel/Filamentによる外部バックエンド）に続き、
**Shopifyのアプリ拡張領域**を担当する。

第1弾で構築した架空の日本茶D2C `chanoka` のデモストアに、実際にインストールして動かす。

## 何を作るか

**日本の贈答EC特有の「のし・ギフト対応」を、Shopifyアプリとして実装する。**

お茶は日本の贈答品の代表格であり、`chanoka` ブランドの世界観と必然的に噛み合う。
かつ熨斗・表書き・名入れ・外のし／内のしは Shopify 標準が構造的に持たない領域で、
日本の Shopify 案件で実際に頻出する要件でもある。

「技術を展示するための機能」ではなく「発注者が実際に困っていることを解く機能」を
選んだのが本作品の設計方針。

## 確定事項（2026-08-13）

| 論点 | 決定 | 理由 |
|---|---|---|
| 熨斗の指定単位 | **商品単位**（cart line attributes） | 「この茶葉は御中元、こちらは熨斗なし」が実務では起きる。Cart Transform の公式例も line attribute ベースで相性が良い。注文単位から商品単位への後付け拡張は困難なため最初から商品単位で作る |
| 入力UIの配置 | **カートページのみ** | 実装・検証が1箇所で済み、複数商品の熨斗をまとめて設定できて操作としても自然。チェックアウト内は Plus 限定で使えない |
| 公開のタイミング | **フェーズ2まで作り切ってから** | Functions を2種類（Cart Transform / Discount）踏め、購入から受注業務まで通しで見せられる状態になる |
| 配布形態 | **extension-only app / custom distribution** | バックエンド・OAuth・ホスティングが不要（費用0円で恒久的に動かせる）。App Store 公開の道は取らない |
| 数量2以上の行の扱い | **行単位で1つの熨斗**。のし料は数量分課金。**包装料も数量分になる**（expand のコンポーネント数量に行数量が掛かるため。2026-08-13 実測） | 別の熨斗にしたい場合は商品ページから別途カート投入すれば、属性が違うため Shopify が自動で別行にする。行より細かい粒度が要るのは「贈り先ごとに配送先が違う」場合だが、**複数配送先への別送はスコープ外**なので現時点では不要。別送を実装する日が来たら数量1への強制分割へ移行する必要がある |
| 受注後の訂正 | **注文メタフィールドに訂正値を持たせる**（フェーズ2） | 確定した注文の line item properties は編集できない。注文メタフィールドは更新可能なので、Admin block に訂正UIを置き、印字用データはメタフィールドがあればそちらを優先する |
| のし・包装料の税区分 | **茶葉は軽減税率8%、のし・包装料は標準税率10%**。2026-08-13 に国税庁の資料で解釈を確認し、開発ストアで実測して成立を確認済み（下記「リスク9」） | 茶葉は飲食料品、有料の贈答用包装は役務提供という一般的な整理による。1注文に2つの税率が混在する。**税率の解釈もShopify側の設定手順もこの時点では未検証**であり、着手時に管理画面の実物と公的な情報で確認する |

## アーキテクチャ

**extension-only app** として構成する。Theme App Extension・Shopify Functions・Admin UI Extension
のみで構成し、開発者側のWebサーバーを持たない。Shopify が全てをホストする。

- 参考: [Build an extension-only app](https://shopify.dev/docs/apps/build/app-extensions/build-extension-only-app)
- 制約: extension-only app は **custom distribution 限定**。App Store での公開はできない
- 帰結: 月額のホスティング費用が発生しない。ポートフォリオは「今すぐ動いて見られる」ことが
  価値なので、維持コストが0であることを積極的に選んでいる

## 見せ方（デモ資材）

**本作品の成果の大半は、管理画面かチェックアウトの中にしか現れない。**
第1弾はストアURLとパスワードを渡せば見せられ、第2弾はGitHubの公開リポジトリで
実装過程が追えたが、第3弾はどちらの方法でも Admin UI Extension と Functions の
動作を発注者に見せられない。管理画面のアクセス権を渡すことはできないため、
**デモ資材の作成を実装と同格の要件として扱う。**

最低限そろえるもの:

- カートで熨斗を指定 → のし・包装料が加算される流れ（画面録画）
- 一定金額到達で包装料が無料になる瞬間（画面録画）
- 注文詳細ページの熨斗情報カード（スクリーンショット）
- 熨斗の印字用データ出力と、受注後の訂正操作（スクリーンショットまたは画面録画）

これを後回しにすると、フェーズ2完了時点で「作ったが見せられない成果物」になる。

## 設計判断の理由（明文化）

**なぜ Cart Transform expand を使うのか（`/cart/add.js` で料金商品を直接追加しないのか）**

単に料金行を足すだけなら、フロントから のし・包装料商品をカートに追加する方が実装も
テストも単純である。それでも expand を選ぶ理由は次の2点。

- 別行として追加すると、**顧客がのし・包装料の行だけを削除できてしまう**
- 親商品を削除しても、**のし・包装料の行が孤児として残る**

expand は親行にコンポーネントとして束ねるため、この2つが構造的に起きない。
「Functionsを使いたいから使う」のではなく、整合性の担保が理由であることを
READMEにも明記する。

## やらないこと

- **チェックアウト内（情報・配送・支払いステップ）へのUI追加** … Shopify Plus 限定のため。
  ここに依存すると案件対象が狭まり、デモも動かせない可能性がある
- **App Store への申請** … プライバシーポリシー・サポート体制・GDPR webhook 等の審査対応は
  Shopify の実装力の証明とほぼ無関係で、費用対効果が悪い
- **第1弾・第2弾との技術統合** … スタックを意図的に分けているのが3作品の構成意図

## 検証結果

### リスク6: 開発ストアへのインストール（2026-08-13）

**開発時プレビューと恒久インストールは別物であり、前者に custom distribution は要らない** —
第三者レビューの指摘が正しかった。

確認できたこと（Shopify CLI 4.6.1 / Node v24.12.0）:

- `shopify app init --template none` で extension-only 相当のプロジェクトが作れる。
  ただし `none` は**空ではない**。App Home（`admin.app.home.render`）・App Tools
  （`admin.app.tools.data`）の2つの UI Extension と、サンプルの FAQ Metaobject・
  商品メタフィールド定義が `shopify.app.toml` に入った状態で生成される
- `shopify app dev --store chanoka-demo.myshopify.com` は**何の配布設定もしないまま通り**、
  管理画面の「アプリ > インストール済み」に当該アプリが並ぶ。アクセススコープも
  `Access scopes auto-granted` として自動付与される
- ただしこれは Dev Console に「開発プレビューをクリーンアップ」と出る**一時的な状態**であり、
  恒久インストールではない
- 恒久インストールについては、公式ドキュメントの
  `Extension-only apps can only be installed with custom distribution.` という記述を再確認した。
  **実際に custom distribution を設定して入れ直すところまでは未検証**

**未検証で残っている点**: `shopify app deploy` でバージョンを作り、Dev Dashboard で
custom distribution を設定してインストールリンクから恒久インストールする経路。
Shopify の配布形態の選択は**後から変更できない**ため、実行前に判断を確定させること。

### テンプレート同梱物の扱い（2026-08-13 決定）

`shopify app init --template none` が同梱する App Home・App Tools・FAQ Metaobject は
**すべて削除した**。判断の根拠:

- **App Home**（`admin.app.home.render`、FAQ管理のデモ画面）… 構成要素#2「表書きマスタを
  マーチャントが管理画面から増減できる」は、Metaobject 定義に
  `access.admin = "merchant_read_write"` を書けば**標準の管理画面だけで満たせる見込み**の
  ため、自前の管理UIは重複と判断した。管理画面での見せ場は構成要素#5（受注画面の熨斗カード）で
  確保できる。**ただし下記の未検証点あり**
- **App Tools**（`admin.app.tools.data`）… Shopify の AI アシスタント向けにツールを公開する
  拡張。requirements.md の範囲外で、のし・ギフト対応の実装力の証明とも無関係。
  `shopify.app.toml` の `[sidekick]` 節も併せて削除
- **FAQ Metaobject / 商品メタフィールド定義** … デモ用のデータモデル。表書きマスタの定義に
  置き換えるため削除。**書き方は本コミットの親 `a11711e` に残してある**ので、実装時は
  そこを参照すればよい
- 併せて `shared/`（FAQ用のモデルとGID変換）と `vite.config.ts`（存在しない `home`
  ディレクトリを `root` に指定しており、App Home 削除後は完全に宙に浮く）も削除

削除後に `shopify app dev` を再実行し、拡張が0個の状態でも
`✅ Ready, watching for changes in your app` まで到達することを確認済み。

**この判断が依存している未検証点（リスク5で必ず確認する）**:
`access.admin = "merchant_read_write"` が、エントリーの**新規作成・削除**まで許すのか、
既存エントリーの**値の編集**だけなのか。公式ドキュメントの表現は
`merchants can both view and edit entries` で、この点があいまい。
**編集しかできないなら App Home の削除判断は覆り、表書きマスタ用の管理UIが必要になる。**

### リスク5前半: 管理画面からの表書きマスタ管理（2026-08-13）

**結論: `access.admin = "merchant_read_write"` で、マーチャントは標準の管理画面から
エントリーを新規作成・編集・削除できる。** App Home を削除した判断は維持する。

確認手順と結果:

- `shopify.app.toml` に `[metaobjects.app.noshi_title]` を宣言し、`shopify app dev` を実行。
  **`shopify app deploy` は不要**で、開発プレビューだけで定義がストアに登録された
- 管理画面「コンテンツ > メタオブジェクト」に「熨斗の表書き」が
  **追加元 `noshi-gift-app`** として並ぶ
- エントリー一覧に「エントリーを追加」ボタンがあり、実際に1件（`ochugen` / 御中元）を
  管理画面から作成して保存できた
- エントリー詳細の「その他の操作」に「エントリーを削除」がある
- `capabilities.publishable = true` により、エントリーごとに Active / Draft の
  ステータスが付く。公開・非公開の切り替えに使える

app-owned Metaobject の型の実体は **`app--<アプリID>--<ハンドル>`**（今回は
`app--410001276929--noshi_title`）。`$app:noshi_title` はこの糖衣。

**ハマりどころ: ハンドルの自動生成が日本語のまま入り、そのままでは保存できない。**
表書きに「御中元」と入れるとハンドルも「御中元」になるが、Shopify は
`ハンドルは小文字にする必要があり、文字、数字、ダッシュのみ使用できます` を要求して
保存を拒否する。マーチャントは毎回ハンドルを手で英字に直す必要がある。
**この体験の悪さは、表書きマスタの管理UIを自前で作る（＝App Home を復活させる）
理由になりうる**ので、フェーズ2の判断材料として残す。

**デモ資材への影響（重要）**: 管理画面のエントリー詳細には
「〈スタッフの氏名〉が追加」と実名が表示される。**公開するスクリーンショットには
実名が写り込む**ため、撮影前にマスクするか、表示名を架空名に変更する必要がある。

### リスク5後半: Liquid からの読み出し（2026-08-13）

**結論: 素のテーマ Liquid から app-owned Metaobject を読める。**
`shopify theme console`（Liquid REPL）で確認した。書き方は下記の通り。

| 用途 | 書き方 | 結果 |
|---|---|---|
| 全件 | `metaobjects['app--<アプリID>--noshi_title'].values` | 7件取得できた |
| フィールド | `entry.label` | `.value` は不要。値が直接返る |
| 単体（ハンドル指定） | `metaobjects['app--<アプリID>--noshi_title'].<handle>` | 取得できた |
| 単体（`.values` 経由） | `metaobjects[...].values.<handle>` | **null。使えない** |
| 添字 | `metaobjects[...].values[0]` | **null。`\| first` を使う** |
| `$app:` 糖衣 | `metaobjects['$app:noshi_title']` | **`Unknown object` エラー。Liquid では使えない** |

**帰結1: アプリID（`410001276929`）を Liquid に書かないと型を解決できない。**
`$app:` は TOML と Admin API 側の記法で、Liquid には通じない。
アプリIDはアプリ固有でストアをまたいで変わらないためハードコードでも動くが、
リポジトリを公開する以上、意味の分からない数値が裸で残るのは良くない。
実装時にブロック設定かスニペットへ切り出して1箇所に閉じる。

**帰結2: `.values` の既定の並びは登録順ではない。** 実測では最後に作った
「無地熨斗」が先頭に来た。`| sort: 'display_order'` を通して初めて
御中元→御歳暮→御祝→内祝→御礼→粗品→無地熨斗 の順になる。
**`display_order` フィールドは必須であって、あれば便利という位置づけではない。**

上記は `shopify theme console` で確認したのち、**app block として実際にストアフロントへ
描画した状態でも同じ結果になることを確認済み**（下記「app block の設置とレンダリング」）。

### Dawn のカートセクションが app block を受け入れるか（2026-08-13）

**構成要素#1の設計に直結する制約が見つかった。**

| セクション | `{"type": "@app"}` の有無 |
|---|---|
| `sections/main-cart-footer.liquid` | **あり**（app block を置ける） |
| `sections/main-cart-items.liquid` | **なし**（app block を置けない） |

つまり **Dawn 標準のままでは、カートの各行の中に熨斗入力UIを差し込めない。**
「確定事項」では熨斗の指定単位を商品単位（cart line attributes）と決めているが、
入力UIの置き場所はカートフッター側になり、そこから各行の入力をどう出すかを
別途設計する必要がある（フッター内に行ごとの入力をまとめて並べる等）。
第1弾のテーマを書き換えて `main-cart-items` に `@app` を足すのは
「触ってはいけないもの」に該当するため採らない。

### リスク4: Discount Function で包装料を無料にする（2026-08-13）

**結論: 「包装料のラインだけを100%割引」はできない。ただし同じ金額の結果は出せる。**
`extensions/noshi-wrap-free`（`cart.lines.discounts.generate.run`）を実装し、
fixture テスト6件と開発ストアでの通し確認を通した。

**できない理由**: Discount Function が見るのは **Cart Transform で expand された
あとのバンドル行**であり、のし代・包装料のコンポーネントは個別の行として現れない。
Discount API のスキーマにも `component` / `bundle` に相当する型は存在せず、
商品割引のターゲットは `cartLine { id }` だけ。

**採った回避策**: 包装料と同額（¥300）の `fixedAmount` を、`appliesToEachItem: true` で
バンドル行に当てる。数量分の包装料がちょうど相殺される。
顧客からは「包装料 ¥0」ではなく**「包装料無料」という割引行**として見える。

実測（しきい値 ¥3,000 / 抹茶 ¥2,400）:

| ケース | 小計 | 割引 | 合計 |
|---|---|---|---|
| 熨斗あり × 1 | 2,800（しきい値未満） | 0 | ¥2,800 |
| 熨斗あり × 2 | 5,600 | 600（300×2） | ¥5,000 |
| 熨斗なし × 2 | 4,800 | 0 | ¥4,800 |

**Cart Transform は Discount より先に走る。** Discount Function が受け取る
`cart.cost.subtotalAmount` には **のし代・包装料が含まれている**。
しきい値を ¥2,600 に下げて数量1（商品代 ¥2,400 / のし込み ¥2,800）で試すと
割引が適用されたことから確認した。

**帰結: 「一定金額以上」の一定金額は、のし・包装料込みの小計になる。**
商品代だけで判定したいなら、Function 側で のし代・包装料の分を差し引く計算が要る。
どちらの仕様にするかは未決。

**仕様の食い違いは解消済み（2026-08-14 決定）**: 構成要素#6は当初「一定金額以上で
**のし・包装料**を無料」と書いていたが、実装に合わせて**包装料のみ**に寄せ、
構成要素の表を修正した。のし代は無料化の対象に含めない。理由:

- この固定額割引は税額計算上バンドル全体に按分される（下記「税務上の限界」）。
  **無料化の対象が少ないほど、按分による帳簿上の誤差も小さい**
- のし（表書きの印字）は役務、包装はサービス訴求という整理が贈答ECとして自然で、
  「のし代は必ずいただく／包装料はまとめ買いのお礼に無料」と説明が通る

のし代も無料にする場合は `noshiFeeAmount + wrapFeeAmount` を引く形になり実装コスト差は
小さいので、方針を変える判断が出たら `$app:noshi_settings` を読む箇所を直せばよい。

**税務上の限界（リスク9で判明）**: この固定額割引は、税額の計算上
**バンドル全体に按分される**。「包装料だけ無料」にはならず、茶葉の課税標準も下がる。
詳細と実測値は下記「リスク9」を参照。

### リスク9: 軽減税率（2026-08-13 調査。実機検証は未了）

#### 税務の解釈: requirements の前提は公的な情報と整合する

国税庁「消費税の軽減税率制度に関するQ&A（個別事例編）」に、包装材料等の扱いがある。

- 飲食料品の販売に付帯して**通常必要なものとして使用される**包装材料等は、
  「飲食料品の譲渡」に該当する（＝8%）
- **贈答用の包装など、包装材料等につき別途対価を定めている場合**の
  その包装材料等の譲渡は、「飲食料品の譲渡」に**該当しない**（＝10%）

本アプリはのし代・包装料を**別建てで課金する**設計なので、後者に当たる。
「茶葉8% / のし・包装料10%」という確定事項の整理はこれで裏が取れた。
出典: <https://www.nta.go.jp/taxes/shiraberu/zeimokubetsu/shohi/keigenzeiritsu/qa_03.htm>

**ただし最終的な税務判断は税理士の領域**であり、ここに書いたのは
公開資料と本アプリの設計を突き合わせた結果に過ぎない。

#### Shopify 側の設定手順

Shopify ヘルプ「Tax overrides and exemptions」より。**管理画面の記憶で書かず、
着手時にこのページを見直すこと。**

1. 対象商品を**手動で追加したコレクション**を作る
   （"You can set up tax overrides only with products that you manually add to collections."）
2. **設定 > 税と関税** → 対象の国 → **税率と免除** の **商品の上書き** → **上書きを追加**
3. コレクションと地域を選び、税率を入力

日本の既定は10%なので、**茶葉のコレクションに8%の上書きを当てる**形になる。
のし代・包装料は既定の10%のままでよい。

**手順1は実施済み（2026-08-13）**: 手動コレクション「軽減税率対象(飲食料品)」
（handle `reduced-tax-rate`）を作成し、日本茶6商品を入れた。
販売チャネルには未公開で、ストアフロントからは404になることを確認済み
（第1弾のコレクション一覧にも出ない）。
ワークショップ参加券・のし代・包装料は飲食料品ではないため入れていない。

#### バンドルでも税の優先適用は無視されなかった（実測）

ヘルプの `Tax overrides on the bundle product itself are ignored at checkout.` が
本アプリに当てはまるかを実測したところ、**当てはまらなかった**。
expand でバンドル親になった茶葉にも8%が効き続ける。
この記述は `requiresComponents` を立てた**バンドル商品そのもの**を指しており、
Cart Transform で expand した通常商品には及ばないと解釈できる。

実測（税込表示・`taxesIncluded: true`）:

| ケース | 合計 | 税額 | 判定 |
|---|---|---|---|
| 熨斗なし 茶葉×1 | ¥2,400 | **¥178** | `2400÷1.08×0.08＝177.8` → **8%** |
| 熨斗あり 茶葉×1（バンドル） | ¥2,800 | **¥214** | 茶葉177.8＋のし包装36.4＝214.1 → **8%と10%が併存** |

全部10%なら前者は¥218、後者は¥255になるはずで、いずれもそうならなかった。
**確定事項の「茶葉8% / のし・包装料10%」は実機で成立する。**

#### 割引はコンポーネントに按分される（リスク4の回避策の限界）

熨斗あり茶葉×2（包装料無料の割引が効く条件）で測ると、
合計 ¥5,000 に対し税額は **¥382** だった。

- もし割引が**包装料だけ**に当たっているなら … 茶葉355.6＋のし代18.2＋包装料0 ＝ **¥374**
- もし割引が**バンドル全体に按分**されているなら … **¥382**

**後者と一致した。** つまり「包装料無料」は税務上そう扱われず、
**¥600 の値引きが茶葉・のし代・包装料に比例配分される。**
その結果、包装料は¥0にならず（実質¥536相当）、**茶葉の課税標準まで下がる。**

顧客が払う総額は意図どおりだが、**税額と内訳は「包装料を無料にした」場合と一致しない。**
リスク4で採った「バンドル行への固定額割引」という回避策の、これが限界。
帳簿の正確さを求めるなら、包装料を別行（expand のコンポーネントではなく独立した
カート行）にする設計に戻す必要があり、その場合は「顧客が包装料だけ削除できる」
という expand を選んだ理由と正面からぶつかる。**フェーズ2で判断する。**

#### 開発ストアに入れた設定（2026-08-13）

| 場所 | 設定値 |
|---|---|
| 税金と関税 > 日本 > 基本税 | 日本 **10%**（都道府県は全て0%） |
| 同 > 税率と免除 > 商品の優先適用 | 軽減税率対象(飲食料品) / 日本 / **8%**（「10%の連邦税の代わり」＝置き換え） |
| 税金と関税 > 追加設定 | **商品価格と配送料に売上税を含める = ON** |

**事業体（組織 > 事業体）は米国のまま変更していない。** 税の計算には影響しなかった。
税込表示にすると「アメリカ合衆国に拠点を置くストアの場合、価格に税金を含めるべきでは
ありません」という警告が出るが、**助言であって動作は妨げない。**
事業体を日本に変えるには法的な氏名・生年月日・住所の入力が必要になり、
本プロジェクトのガードレール（実在情報を持ち込まない）と衝突するため採らなかった。

#### 着手時に詰まった点（記録）

当初 `chanoka-demo` は `taxesIncluded: false`・**日本の基本税が0%**で、
チェックアウトに税額が一切出なかった。リスク1・4の検証で税行が現れなかったのは
このため。**基本税が0%だと、優先適用を入れても他の商品が非課税のままになる**ので、
基本税10%→優先適用8%の順で入れる必要がある。

税込表示（`taxesIncluded: true`）にしたことで、ストアフロントの表示価格は
**¥2,400 のまま変わらない**（内税¥178になる）。税抜のままだと ¥2,592 に見えてしまい、
第1弾のデモストアが実質値上げされたように見えるため、税込にするのが正しい。

### リスク3: カート上での line item properties の後編集（2026-08-14）

**結論: 後から編集できる。ただし `quantity` を省略すると数量が黙って 1 に落ちる。**
構成要素#1（のし入力ブロック）はカートに入っている行の熨斗を編集する UI なので、
この罠を踏むと**顧客のカートから商品が消える**。開発ストアの実機で
`/cart/change.js` を直接叩いて挙動を確定させた。

#### 最重要: `properties` と `quantity` の既定値が非対称

| 送るもの | 送らなかった側の扱い |
|---|---|
| `quantity` だけ送る（テーマ標準の数量±ボタン） | **`properties` は保たれる**。安全 |
| `properties` だけ送る | **`quantity` が 1 にリセットされる** |

実測（衝突なし・素の行×3の属性を変更）:

| 送り方 | 変更後の数量 |
|---|---|
| `{id, properties}` | **1**（3が失われる） |
| `{id, quantity: 3, properties}` | 3（正しい） |

**帰結: properties を更新するときは、必ずその行の現在の数量を `quantity` に明示して送る。**
この非対称性に気付かないと、当初は「衝突した相手の行が消える」ように見えて原因を誤る
（実際、検証中に「既存行＋1」という規則に見えたのは、変更対象が1に落ちてから
合算されていたため）。

#### 変更後の属性が既存行と一致すると、黙ってマージされ数量は合算される

| 条件 | 結果 |
|---|---|
| 既存「御中元×2」＋「素×3」→ 素の行を御中元へ（`quantity: 3` 明示） | 1行「御中元×5」 |

合算自体は期待どおりだが、**行数が減る**のでブロック側は再描画が要る。
`quantity` を明示しないと「御中元×3」になり、2個ぶんが消える。

#### その他の確定した挙動

- **`properties` は全置換。** `名入れ` だけ送ると `表書き` が消える。
  表書き・名入れ・のし種別は**常に全部まとめて送る**
- **属性のキー自体は削除できない。** 空文字も `null` もキーは残り値だけが空になる。
  `properties: {}` は「変更なし」として無視され、既存の属性がそのまま残る
- **空値の属性は Dawn のカート画面に表示されない**（`property.last == blank` で除外される）。
  金額も素の状態に戻るため、**「熨斗を外す」は空文字を送るだけでよい**。
  Cart Transform 側も `trim()` して無視する実装になっており、挙動が一致している
- **行キー（`key`）のハッシュ部は属性を変えるたびに変わる。** variant ID 部分は不変。
  更新後は新しいキーを取り直す必要がある
- **行の並び順は「後から追加した行が先頭」。** `line` の番号は追加順と一致しないため、
  **`line` ではなく `id`（行キー）で指定する**

**未検証**: 空値の属性が、チェックアウトと Admin の注文詳細でも非表示になるか。
Admin に「表書き: （空）」が出ると出荷担当が混乱するため、構成要素#5 の実装時に確認する。

### リスク10: Admin UI Extensionからの注文情報アクセス・書き込み（2026-08-14 調査。実機実装は未着手）

**結論: 熨斗情報の「表示」はカート行の line item properties をそのまま読めばよいが、
「訂正」は line item 側を書き換えることができない。訂正値は app 独自の Order メタフィールドに
別途保存する設計にする必要がある。** 公式ドキュメント（Admin UI Extensions / Admin GraphQL API）で
確認した。実機での extension scaffold・実装はまだ行っていない。

#### データの取得: `admin.order-details.block.render` の `data` は注文のIDしか渡さない

`BlockExtensionApi.data` は「現在表示・選択中のリソースID の配列」であり、注文の
line item や属性そのものは含まれない。表書き・名入れ・のし種別を表示するには、
`data` から注文の GID を取り、**Standard API の `query()`（Direct API Access。
GraphQL Admin API への `fetch()` は自動的に認証される）で改めて注文を取得する**必要がある。
読みたいフィールドは `Order.lineItems.customAttributes`（cart line item properties は
注文になるとこの名前になる）。

#### 書き込み: line item の `customAttributes` を編集する mutation は存在しない

`orderUpdate` mutation の `OrderInput.customAttributes` は **注文レベル**
（`Order.customAttributes`）を上書きするフィールドで、`LineItem.customAttributes`
（各行の熨斗情報）を編集する経路ではない。Admin GraphQL API を横断して調べたが、
line item の custom attributes をチェックアウト後に書き換える mutation は見当たらなかった
（顧客がカートで入力した内容は注文として確定した時点で凍結される、という一般的な
Shopify の設計と整合する）。

**帰結: 出荷担当による「訂正」は、確定済みの line item properties を上書きするのではなく、
app 独自の Order メタフィールド（例: `$app:noshi_correction`）に訂正後の値を追加で持たせ、
Admin UI Extension 側は「元の入力」と「訂正後の値」を両方表示する設計にする。**
元データを消さずに訂正の記録を残せるという利点もある。

#### 書き込みに必要なスコープ

- Order を owner とする metafield を書くには `metafieldsSet` mutation を使う。
  Order owner への書き込みには **`write_orders` スコープ**が要る
  （`read_orders`/`write_orders` は Order owner の metafield 読み書き権限も兼ねる。
  公式ドキュメントで個別の narrower scope は確認できなかった）
- Direct API Access は既定で **online access mode**。本アプリの `shopify.app.toml` は
  `[access.admin] direct_api_mode = "online"` / `embedded_app_direct_api_access = true`
  を既に設定済みのため、追加設定は不要。`scopes` に `write_orders` を追加するだけでよい
- **60日より前の注文は既定でAdmin GraphQL APIから見えない。** 過去の注文を読むには
  `read_all_orders` スコープが追加で必要（`read_orders`/`write_orders` と併用）。
  App Store 提出時は Shopify の審査で用途を問われる可能性があるスコープなので、
  実装時に「直近の注文だけで足りるか」を確認してから要否を判断する

#### 未検証（次の実装フェーズで行うこと）

- `shopify app generate extension --template admin_block` で実際に scaffold し、
  `query()` で注文の line item properties を取得できるか実機確認
- `metafieldsSet` で Order メタフィールドへの書き込みが通るか実機確認

### 設定値の一元化（2026-08-14）

**variant ID・単価・しきい値を shop metafield `$app:noshi_settings`（type: json）へ一元化した。**
`noshi-fee`（Cart Transform）と `noshi-wrap-free`（Discount）の両方が入力クエリで
`shop { metafield(namespace: "$app", key: "noshi_settings") { jsonValue } }` を読み、
片方だけ直して金額がずれる事故を構造的になくした。

- 定義は `shopify.app.toml` の `[shop.metafields.app.noshi_settings]`。
  マーチャントが管理画面から誤って書き換えないよう `access.admin` は付けていない
- 値は JSON 1件にまとめている:
  `{ noshiFeeVariantId, wrapFeeVariantId, noshiFeeAmount, wrapFeeAmount, freeWrapThreshold }`
- 投入は Admin API の `metafieldsSet`（`ownerId` は shop の GID）。
  開発ストアには実測用の値（のし代¥100・包装料¥300・しきい値¥3,000）を投入済み
- 設定が未投入・壊れている場合、両 Function とも**何もしない**（`blockOnFailure: false`
  と同じ考え方で、カートは通す代わりに のし・包装料は加算しない）。fixture テストに
  `settings-missing.json` を追加して確認済み
- 実機確認（2026-08-14）: 熨斗あり×1で合計¥2,800、熨斗あり×2で
  小計¥5,600→割引¥600→合計¥5,000。いずれも一元化前と同じ結果が出ることを確認した

**ハマりどころ**: Shopify CLI の `shopify app dev` が使う GraphiQL の内蔵プロキシは
`/graphiql/graphql.json?key=<起動ログのkey>&api_version=<version>` が正しいパス。
`/graphql.json` だけでは 404 になる。
